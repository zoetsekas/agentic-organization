The spine

Spec → gate → IR → targets

Permissions and authority are resolved exactly once, at the gate. Targets never import the spec, so a runtime cannot disagree with the artifact somebody reviewed.

01

System spec

Teams, roles, capabilities, decisions, mandates, separations, autonomy. Names no cloud, no framework, no product.

02

Phase gate

Resolves permissions and effective authority, checks the mechanics against what was declared, and refuses rather than guesses.

03

IR

One resolved artifact. Diffed by consequence, so a widened permission never reads like a renamed field.

04

Targets

Docker Compose, and Terraform for GCP, AWS and Azure. Same IR, different bindings — local is not a mock.

The org model

Four questions, four answers

Most platforms model the first one. An organization runs on all four, and conflating them is how a control quietly stops being a control.

Permission May this agent do X at all? A missing permission is a dead end — it refuses and stops there. roles · policies
Mandate Was this agent the one to decide it? A decision above your authority belongs to somebody, so it escalates rather than refusing. decisions · conditions
Separation May one principal hold both sides of a control? A team is a scope and may; an agent is a principal and may not. separations
Autonomy How much of this runs without a person? Declared per activity, defaulting to advisory — which may not change a system of record. advisory → autonomous
Boundaries

Who enforces a control

An agentic organization does not replace its enterprise applications. The ERP owns the ledger, the treasury system owns the sweep, the bank owns the payment. So every control says who checks it — because a bound that reads as enforced and is not is worse than no bound.

platform

Ours, and it must be evaluable here or the spec is refused. The default, so claiming a control obliges us to evaluate it.

application

Theirs. We may describe it and may not claim it. The system is named, and the report says what is being trusted rather than checked.

both

Names an authoritative side and is always reported. Two rule sets that can disagree is how a bound gets quietly relaxed on one side.

What the design actually refuses

Built to the conventional CFO structure — Controllership, FP&A, Treasury, Tax, and Internal Audit reporting outside the CFO. These are real messages from the gate and the tool boundary.

payables → release 'release_payment' is outside every mandate above this agent; it is held by treasurer, who is not in this escalation line
cfo · inherited agent 'cfo' holds ['approve_invoice', 'raise_payment', 'release_payment'], which separation 'payment_control' forbids
binding approve_invoice and raise_payment share server 'erp_payables' and credential 'ERP_PAYABLES_ENTRY_DSN'
capability · posture declared advisory but the action is 'write', so it changes a system of record
control ownership claims 'rate_per_minute' as a control this platform enforces, and nothing here evaluates it
phase gate · report ✓ Every control names its enforcer — 2 left to an application: cash_manager → the treasury management system; payment_control → the ERP's own segregation rules
Honest status

Built, contracted, designed

A contract is modelled, tested against a fake, and has never met its real counterpart. A design is a decision nobody has implemented. Both are counted here rather than described as features.
